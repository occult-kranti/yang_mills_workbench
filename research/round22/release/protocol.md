# Round22 release protocol

Complete and skeptically review exactly N1–R2 before creating an inventory. The ten scientific gates and all historical gates stay immutable. The final inventory binds actual admission/replay/renderer sources, every current-round file, current shared guidance, reviewed outputs, all inherited Round21 scientific closure and the separately repaired historical C2 inventory. It excludes only its own path to avoid self-reference. An external reviewed SHA256 pins the candidate; coherent rebinding does not replace that pin. Checkpoints bind their exact reviewed gate set and the ledger binds each contract, submission and checkpoint. The complete claim map is audited before the next-three-goal selection; its future-roadmap reference is a path rather than a circular content dependency.

The integrator must inspect the candidate diff, commit the reviewed staged Git tree, create a clean detached Git worktree, and run final_verify.py there with outputs outside the tree. Supply the independently reviewed --git-commit and --git-tree as well as the inventory digest. The verifier checks detached HEAD, clean status, every inventoried disk blob and executable mode against the committed tree (including ignored/status-hidden cases), exact commit/tree, ancestry from the recovered base, unchanged historical research and inventory coverage of every changed published path. The canonical in-tree inventory must exist and match the supplied inventory bytes. Both Python modes execute all20 current producers and the16 admission rejection controls. Historical replay and C2 repair add no research loops. The claim map and generated Round22 data are removed immediately before their builders, and the Pages destination starts empty. Site data and Pages assets are rebuilt in an external mirror, compared bytewise and checked with the three bound Node suites. The same verify_site stage is directly exercised for build-specific failure controls without replaying unrelated science or mocking acceptance logic. Visual/browser review is separate and must state what was actually inspected.

After verification, the authorized publication must preserve the tested tree. Verify the remote commit/tree separately from the Pages deployment and the live page. A changed remote base requires reassessment; never force-push over unrelated work. Publishing via an authenticated Git data API may create a different commit identity, but must produce the exact tested tree and retain the verified parent. Record local candidate, remote research commit, merge commit, deployment result and live checks separately.

No verification output is inserted into the already pinned inventory after verification. Durable pre-release reviews belong in the candidate; final verification records may be attached to the authorized pull request or recorded in a later documentation-only receipt that does not change scientific or site assets. Do not claim that a later receipt was part of an earlier tested tree.
