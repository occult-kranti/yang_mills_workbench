## 2. Vocabulary audit: did this lens's proposed templates and fields survive into plan.json and the drafts?

**Sub-labels — clean.** All six proposed (`convergence_of_named_constructions`, `common_limit_of_named_constructions`, `boundary_decay_rate_only`, `dynamics_on_compact_windows`, `transfer_to_named_model`, `obstruction_recorded`) are in `plan.json#/vocabulary/sub_labels_allowed`, and both BA1 and BA2 correctly restrict their own `preregistration.sub_labels_allowed` to the subset relevant to a locality loop. No edit needed.

**"Rate in N" vs "rate in a" — the mechanism landed, two loose instances remain.** `plan.json#/vocabulary/gate_fields` keeps `rate_in_N_claimed` and `rate_in_a_claimed` as two permanently separate fields exactly as proposed, and both BA1 and BA2's `gate_fields_required` implement this split (`rate_in_N_claimed: true`, `rate_in_a_claimed: false`) rather than one merged `rate_claimed` field. Both `mandatory_sentence_template`s use "a rate in N" correctly and handle the exclusion as "not a statement uniform in the lattice spacing a" rather than a bare "rate in a" — compliant. But two prose instances of the bare word "rate" without an attached qualifier slipped into BA2, which a whole-sentence scan would flag as an unqualified "rate": `contracts/ba2.json#/parameters/targets/within_family_cauchy` reads "...the O(1/N) rate is the honest polynomial-F rate", and `contracts/ba2.json#/required[3]` (item 4) reads "...at the honest polynomial rate and meet 2.5x10^-10/(N-1)...". Proposed edits: reword both to *"the O(1/N) rate in N is the honest polynomial-F rate in N"* and *"...at the honest polynomial rate in N and meet..."* — the `O(1/N)` notation already carries the meaning, but the literal phrase scanned by `phrase_scan.py` should carry it too, since this lens's own R6 discipline is whole-sentence and phrase-literal, not notation-aware.

**Forbidden phrasings — the real enforcement is sound; the planning document is not a mirror of it, and one Round32 rule is genuinely unenforced.** `tools/phrase_scan.py#/ROUND_FORBIDDEN` (the code every gate actually scans against) is a proper superset of this lens's "newly forbidden" list plus extra project phrases (`'confirms the Z^3 value'`, `'solves/solved/proves the mass gap'`); `plan.json#/vocabulary/forbidden` is a shorter, non-identical planning list. That divergence is cosmetic — nothing in `record_gate.py` reads `plan.json` for forbidden phrases — but it is exactly the kind of cross-file disagreement this lens's own R9 proposal exists to catch, and R9 (`field_mirror_sweep.py`) does not exist yet. More substantively: Round32's carried-forward rule that a bare **"unique" without an explicit "not" in the same clause is forbidden** (this lens's own memo section 3, "Carried forward unchanged from Round32") is present in neither `ROUND_FORBIDDEN` nor `plan.json#/vocabulary/forbidden` nor either contract's `forbidden_phrasings`. It cannot simply be re-added as a bare token, though: AM2's fixed point is legitimately described as existing "uniquely in the anchored ball" (modern lens memo section 2.1), and BA1's own report will need to cite that. Proposed edit, scoped rather than blanket: add to `plan.json#/vocabulary/forbidden` and to `contracts/ba1.json#/preregistration/forbidden_phrasings` / `contracts/ba2.json#/preregistration/forbidden_phrasings` the targeted phrases `"unique ground state"`, `"a unique limit"`, `"unique infinite-volume"`, `"uniquely determines the ground state"` — closing the actual risk (a claim about a state or a limit) without penalizing AM2's already-admitted uniqueness-of-fixed-point language.

**Gate fields beyond `plan.json`'s baseline — present where this loop needs them, absent where it does not.** This lens's proposed Direction-C/D-only fields (`contingent_on`, `named_model_id`, etc.) correctly do not appear in BA1/BA2, since neither loop is Direction C or D; BA1/BA2 instead carry their own loop-specific fields (`state_decay_claimed`, `gns_dynamics_equality_claimed`, `algebraic_not_gns_dynamics` as a control) matching this lens's own template T-A1/T-B distinctions between coefficient decay, state decay and dynamics. No edit needed.

**R6/R7 — already code, matching this lens's proposal closely.** `record_gate.py` already refuses a gate whose `supported_statement`/`decision` carries an affirmative forbidden phrase (R6) or fails to quote `mandatory_sentence_template` as one unbroken span (R7), reading the contract directly rather than trusting the CLI text — this is this lens's own proposal, adopted essentially verbatim, before either loop has even reached production. **R10 remains a documentation claim only**: `plan.json#/contract_rules` says "R10 by the tier vocabulary below," but `freeze_contract.py` has no check that a contract's `tier`/`tier_label` values are members of `preregistration.tier_names_allowed`, nor that the list is a superset of earlier contracts' lists (the R4-style check this lens's memo proposed). BA1 and BA2's own tier lists are, by hand-check, correct subsets of `plan.json`'s nine — but nothing enforces this once a third contract is drafted. Propose either adding the check to `freeze_contract.py` before BB1 drafts, or recording in `plan.json#/history` that R10 is manual-only for now.
